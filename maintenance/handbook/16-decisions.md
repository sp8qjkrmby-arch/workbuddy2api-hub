# 决策记录（ADR 风格）

格式：决策 / 理由 / 代价 / 何时该重新考虑。

## D1 主干锁 v1.10.8，不追社区 v2.2.x

- **理由**：生产在跑的就是它，且与 M-strange v1.10.8 逐字节一致（可交叉验证）；v2.x 是"换心手术"，引入新上游目录/新自更新链，风险与收益不匹配（我们只要"能继续用"）。
- **代价**：拿不到社区在 v2.x 里的新功能/风控修复。
- **重新考虑的信号**：v1.10.8 因上游协议变更而彻底不可用，且社区 v2.x 明确修好了它。

## D2 更新通道自建，不指向第三方仓库

- **理由**：指向别人的 release 等于把可执行代码下发权交出去（供应链风险）。`shell.json.update_mirror` + `WB_UPDATE_REPO` 环境变量给了低成本的自建空间。
- **代价**：要自己出包、自己托管（GitHub release 或静态 JSON）。
- **重新考虑的信号**：长期没有精力维护打包时，可临时指向信任的仓库**并关掉自动安装**。

## D3 仓库用自己这个 fork，不新建

- **理由**：641 条上游历史有价值（可追溯每个改动为什么来）；fork 已是自己的账号，push 权限天然具备。
- **代价**：parent 已消失，GitHub 上 fork 关系是孤立的；`docker-compose`/徽章等仍指向上游，需手工改。
- **配套**：建议改 private（见 `15-security.md`）。

## D4 不做大重构（巨石拆解只做"顺手"）

- **理由**：`wb_proxy.py` 23 535 行 / 1.16 MB、`dashboard.html` 1.07 MB，上游 CHANGELOG 有 17 次 revert 记录，说明大改极易回归；我们没有上游的评审力量。
- **代价**：改动仍然要在大文件里"手术"。
- **纪律**：只在必须改的区域抽函数/抽模块，不改行为，每步过门 2。

## D5 代码维护与"通道续命"并行

- **理由**：真正的死因是腾讯侧风控/封号，不是代码。代码维护得再好，通道断了也没用。
- **动作**：关注上游协议漂移（UA/指纹/接口），同时评估"同一套 OpenAI 兼容层能否接别的 provider"。
- **代价**：需要额外精力。

## D6 基线用哈希锁定，不用版本号

- **理由**：项目存在"release tag ≠ 包内 version"的双轨问题（`04-versions.md`）。
- **代价**：每次换源都要算哈希（脚本 10 秒）。
- **纪律**：`maintenance/verify-trunk-baseline.ps1` 必须常绿。

## D7 生产实例只在"脱离会话"的方式下重启

- **理由**：这个对话的模型请求也走 8788；硬停会打断自己，且可能留下半完成状态。
- **代价**：重启多一道"排计划任务"的手续（已脚本化）。
- **重新考虑的信号**：如果将来 DSH 改走别的出口，可直接重启。

## D8 备份每日自动、保留 30 份、含代码

- **理由**：数据（账号/账本）不可重建；代码虽在 git，但部署态与仓库态可能不一致（本机就不一致过一次）。
- **代价**：约 19 MB/天，30 份约 570 MB。
- **纪律**：备份目录按机密数据处理。
